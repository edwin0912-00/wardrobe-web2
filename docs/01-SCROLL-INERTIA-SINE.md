# Скрол, інерція, синусоїда — годинник сайту

Усе в `engine.js`. Один принцип: **скрол пише одну ціль, окреме значення її наздоганяє,
і саме це друге значення керує фільмом.** Нічого іншого фільм не читає.

## Скрол → ціль

`readTarget()` бере `window.scrollY / (root.scrollHeight - viewport())`, затиснуто в 0..1.
Це `target`. Рушій ніколи не перехоплює нативний скрол — трекпад, клавіатура, зворотний
скрол працюють як завжди, бо `wheel`/`touch` не блокуються.

## Ціль → поточне (інерція)

```
delta = target - current
current += delta * config.inertia   // дефолт 0.085
```

Це експоненційне наздоганяння: кожен кадр `current` проходить 8.5% залишку відстані до
`target`. Тому свайп відчувається як вага, а не як прив'язаний повзунок. `config.inertia` —
єдине число, що це керує.

## Швидкість (для звуку й зерна)

`speed` — публікується як `--speed` на корені й передається в `onSpeed`. Два згладжування,
не одне: `instant = |moved| / speedFullScale` (дефолт 0.006), тоді:
```
attack:  speed += (instant - speed) * 0.5    // швидко росте
release: speed += (instant - speed) * 0.06   // повільно згасає
```
Атака швидша за спад навмисно — флік розквітає і потім осідає, а не клацає.

## Синусоїда — і чому вона НЕ на клоковому часі

Наївний підхід — `easeSine(localProgress) * duration`. Це не працює, бо матеріал сам по собі
рухається нерівномірно (зміряна нерівність 0.35–0.92 від середнього по трьох ногах) —
згладжування ЧАСУ складається з нерівністю матеріалу, а не виправляє її.

Натомість `motion-table.py` (офлайн, разово на кожен майстер):
1. Міряє реальний рух кадр-до-кадру в майстрі (mean abs diff, 320px аналіз-ширина, 129 семплів)
2. Інтегрує цей рух у кумулятивну криву
3. Інвертує її проти бажаної sin-кривої: `sine_cumulative(u) = 0.5 - 0.5*cos(π*u)`
4. Записує `t = np.interp(want, cum, times)` — готову таблицю скрол-прогрес → час відео

Результат — `b/motion.json`, по одній таблиці на ногу. Перевірено на реальному матеріалі:
кореляція з `sin(πu) = 1.0000`, пік точно на 0.500, найгірша похибка кроку 0.01%.

`tableLookup(table, u)` — лінійна інтерполяція по цій таблиці. `timeFor(idx, local)` віддає
перевагу таблиці; easeSine по клоковому часу лишається лише як fallback, якщо таблиця не
завантажилась (мережева помилка чи відсутній файл) — деградація, не дизайн.

**Пастка, у яку я сам вступив:** після переконвертації майстрів на 60fps один файл втратив
1 кадр (обрізка дубля), і `b/motion.json` для тієї ноги вказував на 17мс ЗА межу файлу.
Рушій це затискав мовчки (без краху), але останні мс таблиці були мертві. Виправлено:
таблицю треба перебудовувати або затискати (`min(x, real_duration - epsilon)`) щоразу,
коли міняється тривалість файлу — бекап старої лишати як `.bak`.

## Шов між сценами

`seamWindow` (дефолт рушія 0.10, канонічний сайт виставляє `0`) — частка ноги,
де сусідня сцена підмальовується поверх поточної. Зміряно на реальних майстрах: кінець
ноги N проти початку ноги N+1 різниться в середньому на 2.5% яскравості пікселя (4–5.6%
пікселів вище порогу) — тобто кадри майже ідентичні, і різкий різ майже нічого не приховує.

Для цих master-файлів сайт використовує точний cut: короткий fade створює подвійну
експозицію, бо камери не зареєстровані піксель-в-піксель. Fade лишається тільки для
окремого переходу textile intro → перша кімната.

**Баг, знайдений і виправлений:** `config.seamWindow || 0.10` вважав `0` відсутнім значенням,
тож явний запит на чистий різ (`seamWindow: 0`) тихо повертав дефолтні 10%. Тепер
`config.seamWindow == null ? 0.10 : config.seamWindow`.

Компонування шва: нижній шар лишається ПОВНІСТЮ непрозорим, верхній наростає — не обидва до
0.5. Два шари по 0.5 поверх чорного дають 0.75 яскравості замість 1.0, тобто шов би темнів.
