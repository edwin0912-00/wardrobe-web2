# План: повний злив workspace на GitHub як хендоф-референс

**Статус: НЕ ВИКОНУВАТИ.** Записано за прямою вказівкою оператора — робити це
тільки після того, як beta дійде до робочої мінімальної версії (MVP), яку можна
чесно тестувати. Цей файл — план, а не задача в роботі.

## Що сказав оператор дослівно (парафраз його коментаря)

Треба попросити Claude Code залити весь workspace — з усіма логами, усіма
коментарями, усіма хендоф-командами, посиланнями на матеріали й файли,
конкретними веб-сторінками, повною структурою й архітектурою — на GitHub, в
окрему гілку від основного сайту (не в `beta`, не в `main`), до якої будь-хто
звертатиметься за хендофом для будь-якого агента. Але **не зараз** — тільки
після того, як дійдемо до працюючої мінімальної версії, щоб дизайном і рештою
все ще керував Claude Code.

## Навіщо це окрема гілка, а не те, що вже є в `handoff/`

Те, що вже є (`handoff/GITHUB_AGENT_HANDOFF.md`, `LIVE_STATUS.md`,
`ops/RUNTIME.json`) — це живий, короткий, машинно-читабельний хендоф для агента,
що продовжує роботу прямо зараз. Те, що просить оператор — це повний архів:
включно з речами, які живий хендоф свідомо НЕ несе, бо вони важать і не
змінюються щохвилини:
- локальні шляхи медіа (`~/Desktop/ZEELY_REVIEW_20260727` і подібні),
- повні транскрипти воркфлоу (`journal.jsonl` файли),
- знімки станів по датах (`CURRENT_STATE_*`, `STATUS_*`),
- історія рішень і чому вони такі, а не тільки поточний стан.

Тобто це не заміна живому хендофу, а його архівний старший брат.

## Кроки (коли настане час)

1. **Інвентаризація.** Пройтись по всіх джерелах: `handoff/**`, `docs/**`,
   `ops/**`, `updates/**`, локальні медіа-теки на кожній машині, транскрипти
   воркфлоу з `~/.claude/projects/*/subagents/workflows/`. Скласти єдиний
   маніфест — що є, де лежить, скільки важить.
2. **Вирішити, що йде в Git, а що — посиланням.** Великі медіа (папка
   перегляду фотозйомок, style-units із бінарними шитами) не варто дублювати в
   Git другий раз, якщо вони вже там — досить точних шляхів. Локальні файли,
   яких у Git нема (скріншоти, локальні нотатки), копіювати в архівну теку.
3. **Нова гілка**, назва на кшталт `handoff/full-archive-<дата>` — свідомо не
   `main` і не `beta`, щоб не заважати робочому потоку і не проходити через
   правила fast-mode `beta`.
4. **Структура гілки**, орієнтовно:
   - `ARCHIVE_INDEX.md` — головний вхід, що де шукати;
   - `logs/` — усі `LIVE_STATUS.md` за датами, знімки станів;
   - `decisions/` — рішення оператора з датами й обґрунтуванням (витяг з
     канонів і хендоф-документів);
   - `materials/` — посилання (не копії, якщо великі) на медіа-теки;
   - `architecture/` — структура репозиторію, карта продукту (`PIPELINE.md`),
     карта провайдерів (`ops/RUNTIME.json` знімок);
   - `prompts/video/` — точні промти, якими реально генерувались відео-кліпи.

### Про промти відео (уточнення оператора, 2026-07-29)

Оператор явно попросив зберегти промти, якими генерувалось відео — вони
знадобляться, щоб зробити версію 9:16 (дзеркало) з одним дзеркалом окремо від
телевізійної 16:9. Перевірено зараз: **промт не губиться і не живе в чиємусь
чаті** — `VideoService.createJob` (`src/web/video-service.js`) пише повний
скомпільований `plan.prompt` у `metadata.prompt` кожного `clipId` при збереженні
джоби. Тобто коли Antigravity чи хтось інший реально згенерує перші кліпи,
точний промт кожного дістається з job-метадани за `clipId`, а не переказується.

Для архіву це означає: не потрібно окремо «випрошувати» промти в іншого агента
чи чату — досить на етапі інвентаризації (крок 1) пройтись по збережених
`video_clips` у профілях і витягти `metadata.prompt` кожного разом із
`mode`/`surface`/`durationSeconds`. Канонічні шаблони промтів (без конкретного
style-note) лежать статично в `src/web/video-motion-plan.js` — це джерело
правди для того, «як має виглядати» промт незалежно від того, які кліпи вже
реально згенеровані.
5. **Одна команда для читання**, за тим самим принципом, що й
   `GITHUB_AGENT_HANDOFF.md`: агент клонує цю гілку окремо (read-only,
   `--single-branch`) і отримує повний контекст без доступу на запис у робочий
   потік.
6. **Оновлення.** Ця гілка не living-документ у реальному часі — оновлюється
   разово на важливих віхах (кінець MVP, великий реліз), а не щогодини. Живий
   стан і далі веде `handoff/` у `beta`.
