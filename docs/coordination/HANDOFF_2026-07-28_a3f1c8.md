**Design intent, for context on why the module looks the way it does:**
- The web service **never calls a provider directly** — `src/providers/*` is not imported by
  `motion-service.js`. Higgsfield/Magnific are MCP-only, and MCP sessions belong to an agent, not
  a long-running web process. The service emits a job; an injected `motionExecutor.executeMotion()`

  module was drafted, not yet cross-checked for interface compatibility with the

  a real executor in.**).
- Four gates from `config/post-shoot-pipeline.json`'s `VIDEO.*` nodes are enforced, one place

  `ALLOWED_PRESET_ONLY` (route comes from the mode catalogue only, a caller can't name a model),
  `EXPLICIT_PAID_CREATE` (creating a job spends nothing; running it needs

  checked via the existing `receiptDefects()` from `motion-contract.js`; a failing receipt is
  logged in full and no clip is saved).
- Persistence follows the house pattern from `EditorialShootService` /
  `SceneService`: `atomicWrite` for mutable state, `writeImmutable` (write-then-link, EEXIST →
  byte-compare) for artifacts/events, canonical-JSON hashing, deterministic id =
  `motion_${sha256(idempotencyKey).slice(0,48)}`, per-job mutation serialisation via a promise
  chain.

## 4. Item-lock conflict — resolved in principle, NOT yet coded

Full research is at
`/private/tmp/.../scratchpad/units/LOCK-CONFLICT-RESEARCH.md` (session-local; copy it into the
repo's `docs/coordination/` if it should survive past this session).

**The conflict:** operator Edwin's decision is "lock on first appearance" — an avatar is always
locked (incl. feet); a first shoot/video does NOT require pre-locked footwear/bottom; the moment
an item first appears anywhere, capture it, dossier it, hash it, lock it for everything after.
Codex's commit `58dd637` implemented the opposite-in-spirit **pre-generation** gate:
`assertFullLookForEditorialCoda` in `src/web/scene-service.js:458` (call site `:2654`) throws
`422 FULL_LOOK_ITEMS_REQUIRED` unless top+bottom+footwear are ALL bound as approved items **before**
generating the `wide_campaign_coda` slot.

**Data reality that makes this acute:** all 42 runtime scenes on beta have items in categories
`top`×39, `headwear`×1, `outerwear`×1 — **zero bottom, zero footwear**. So the 422 currently fires
on every existing look's coda, unconditionally.

**Resolution reached this session (verbal, not yet coded — the operator corrected an
over-simplified read of it mid-session, see below):**
- Refusal-to-refuse is the wrong axis. The right axis is **where the item's pixels actually
  live**, not whether a category row exists in the item registry:
  1. **Registered item exists** → use it (existing behaviour, unchanged).
  2. **Not registered, but visible in a full-body look** → crop it out of THAT look, lock it as
     `SYNTHETIC_LOCKED`/observed (mechanics already exist in `58dd637`'s
     `outfit-locked-black-trousers` / `outfit-black-sneaker` fixture items — just not applied
     generally), then proceed.
  3. **Not registered, not visible anywhere (a true top-only look)** → the ONLY case where
     invent-once-then-lock applies.
- **Operator's live correction mid-session** (verbatim intent): the 422 gate as coded doesn't
  distinguish these — it treats "no row in the registry" as "must invent or block" even when the
  look is **full-body and the garment is already visible in frame**, in which case the correct
  behavior is capture-and-lock from the existing pixels, never invent a replacement, and never
  block. Blocking a full-body look because bottom/footwear aren't *registered as separate items*
  (when they're plainly *in the picture*) is the bug.
- **Minimal fix, not yet implemented:** `assertFullLookForEditorialCoda` should not be a hard
  pre-check against the item registry. It should become: for each of top/bottom/footwear, resolve
  via branch 1/2/3 above; only branch 3 with NO visible pixels at all is a genuine block; branches
  1 and 2 both produce a locked item and let generation proceed. This turns the 422 into a rare
  edge case (top-only look asking for a coda with literally nothing below frame) instead of the
  default outcome for every existing look.
- **Not yet touched:** the actual code change to `scene-service.js`. This needs care because
  `scene-service.js` is a large, heavily-tested file and touching `assertFullLookForEditorialCoda`
  risks the same kind of collision that already happened once (two IN_PROGRESS rows both reserving
  `editorial-shoot-bible.js` earlier this project). **Check the board for a live claim on
  `scene-service.js` before editing it.**
